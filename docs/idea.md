A few notes on the design choices, since the interesting parts of an app like this are mostly in the model rather than the pixels:
The two-screen flow. The left screen is the part that distinguishes a "Connect" app from a generic remote: it lists every device currently logged in to the Deezer account along with their state (playing, idle with a last-seen timestamp, offline). Picking a device transfers control rather than starting playback fresh — if your desktop is already mid-track, the phone slides into the existing session at 1:23 instead of restarting from zero. That handoff behavior is what made Spotify Connect and the old Deezer Connect feel different from casting.
State has to be eventually consistent across devices. The phone is a thin controller; the desktop is the actual player. Every transport action (play, pause, seek, volume, queue reorder) is a command sent to a backend, which fans it out to whichever device is currently the "active session." The desktop in turn streams its state back (current track, position, queue, volume) so the phone UI reflects reality even if someone bumped the spacebar on the desktop. In Deezer's old implementation this rode on their websocket infrastructure — a reimplementation would either reuse the same channels (if you've reverse-engineered them) or build a small relay server of your own and have the desktop client poll/subscribe to it.
Three control axes. Worth thinking of these as separate concerns rather than one undifferentiated "remote":

Transport — play/pause/skip/seek. Latency-sensitive; needs to feel instant.
Queue and library — view what's coming up, drag to reorder, add tracks, switch playlists. This is where the API surface gets big; you need the same playlist/album/track endpoints the regular app uses.
Output — volume, and which device is the sink. The "Playing on Desktop PC" strip at the top of the second screen is the persistent reminder that this is the third axis.

The bits the mockup glosses over. A real implementation would also need a queue/up-next view (the list icon at the bottom opens it), a search screen (so you can change what's playing, not just control it), and probably a "this device" mode where the phone itself becomes the player. There's also the question of what happens when the controlled device goes offline mid-session — the cleanest pattern is to gray out the controls, surface a "Desktop disconnected" banner, and offer to take over playback locally.
If you do get API access figured out, the lift is mostly: a websocket-or-equivalent state channel, a device registry keyed on account, and a small command protocol (play, pause, seek, next, prev, set_volume, set_queue, transfer_to). The UI is the easy half.
